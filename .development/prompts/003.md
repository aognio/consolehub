Before implementing any code, establish a disciplined development workflow. Treat this project as if it were intended for long-term maintenance by a professional engineering team.

## Development Workspace

Create a `.development/` directory containing at least:

.development/
    architecture.md
    plan.md
    roadmap.md
    backlog.md
    journal.md
    decisions.md
    conventions.md
    assumptions.md
    milestones.md
    testing.md
    security.md
    performance.md
    deployment.md
    api-notes.md
    ui-notes.md
    known-issues.md
    future-ideas.md

These documents should evolve during implementation and remain synchronized with the codebase.

------------------------------------------------------------
Planning First
------------------------------------------------------------

Do not immediately start implementing features.

Instead:

1. Understand the requirements.
2. Review the entire repository.
3. Identify reusable components.
4. Produce an implementation plan.
5. Identify risks.
6. Identify unknowns.
7. Break the work into small milestones.
8. Only then begin implementation.

Whenever a better architecture is discovered, document the reasoning before changing direction.

------------------------------------------------------------
Git Discipline
------------------------------------------------------------

Initialize or reuse a local Git repository.

Create a long-lived working branch:

wip

Do all development there.

Commit frequently.

Prefer many small commits over large commits.

Each commit should represent one coherent logical change.

Examples:

- Initial project structure
- Configuration loading
- PocketBase integration
- Authentication
- Stream ingestion
- Console viewer
- Search
- Mobile layout
- Tests

Write meaningful commit messages.

------------------------------------------------------------
Development Journal
------------------------------------------------------------

Maintain `.development/journal.md`.

Record:

- what was implemented
- architectural discoveries
- rejected alternatives
- unexpected problems
- important implementation notes
- ideas worth revisiting later

This document should make it possible for another engineer to understand the evolution of the project.

------------------------------------------------------------
Decision Log
------------------------------------------------------------

Maintain `.development/decisions.md`.

Whenever a significant architectural decision is made:

- describe the alternatives
- explain why they were rejected
- explain why the chosen solution won

Think in terms of Architecture Decision Records (ADRs), but keep them lightweight.

------------------------------------------------------------
Backlog
------------------------------------------------------------

Maintain `.development/backlog.md`.

Separate items into:

- Critical
- High
- Medium
- Low
- Nice to Have

Move completed items into a Completed section rather than deleting them.

------------------------------------------------------------
Roadmap
------------------------------------------------------------

Maintain version planning.

Example:

v0.1

- infrastructure
- configuration
- authentication
- PocketBase schema

v0.2

- streaming
- live console
- search

v0.3

- multi-host dashboard
- mobile improvements
- administration

Future

- remote control
- metrics
- plugins
- alerts

------------------------------------------------------------
Test-Driven Development
------------------------------------------------------------

Follow TDD whenever practical.

Cycle:

Red

Green

Refactor

New functionality should normally begin with tests.

Maintain high unit-test coverage for business logic.

Use integration tests for:

- authentication
- API
- PocketBase
- streaming
- permissions

Avoid brittle UI tests.

------------------------------------------------------------
Continuous Refactoring
------------------------------------------------------------

Leave the code cleaner than you found it.

Avoid accumulating technical debt.

Extract reusable components early.

Avoid duplication.

------------------------------------------------------------
Code Quality
------------------------------------------------------------

Prefer:

- readability
- simplicity
- explicitness
- maintainability

Avoid:

- premature optimization
- unnecessary abstractions
- speculative features
- giant files
- giant functions

Keep packages cohesive.

------------------------------------------------------------
Documentation
------------------------------------------------------------

Public packages should be documented.

Complex algorithms should explain the reasoning rather than merely describing the code.

Keep documentation synchronized with implementation.

------------------------------------------------------------
Error Handling
------------------------------------------------------------

Errors should:

- contain useful context
- be wrapped appropriately
- never be silently ignored

Avoid panic except for unrecoverable programmer errors.

------------------------------------------------------------
Configuration
------------------------------------------------------------

Avoid hardcoded values.

Everything environment-specific belongs in configuration.

------------------------------------------------------------
Security
------------------------------------------------------------

Assume every external input is untrusted.

Validate early.

Escape output.

Protect authentication endpoints.

Never log secrets.

------------------------------------------------------------
Performance
------------------------------------------------------------

Write clear code first.

Profile before optimizing.

Document any optimization motivated by actual measurements.

------------------------------------------------------------
Implementation Philosophy
------------------------------------------------------------

Build a minimal but solid foundation.

Prefer incremental progress through many small, verifiable steps.

Every completed milestone should leave the project in a buildable, testable, and deployable state. and start working ASAP.
