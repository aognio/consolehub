Extend the backend design to use **JSON-RPC 2.0 over WebSockets** as the primary real-time ingestion protocol.

The WebSocket layer must be treated as a transport adapter over the same application services used by HTTP ingestion. Do not place business logic directly inside WebSocket handlers.

## Connection flow

1. Client opens the configured WebSocket endpoint.
2. Client authenticates.
3. Client registers the running process.
4. Client streams text or JSON lines in batches.
5. Client periodically sends heartbeats.
6. Client reports process completion before disconnecting when possible.
7. Server may send acknowledgements, configuration updates, warnings, or future control requests.

Use standard JSON-RPC 2.0 request, response, notification, and error objects.

Recommended endpoint:

```text
GET /api/v1/rpc/ws
```

## Authentication

Support either:

* Bearer token in the WebSocket upgrade request.
* A first JSON-RPC call named `auth.authenticate`.

Suggested request:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "auth.authenticate",
  "params": {
    "token": "client-token"
  }
}
```

Do not accept ingestion calls until authentication succeeds.

## Recommended client-to-server procedures

### `process.register`

Registers one execution of an app.

Parameters:

```json
{
  "tenant": "tenant-slug-or-id",
  "app": "telegram-replicator",
  "host": {
    "hostname": "vps-01",
    "display_name": "Main VPS",
    "platform": "linux",
    "architecture": "amd64"
  },
  "process": {
    "client_run_id": "uuid-generated-by-client",
    "pid": 42817,
    "parent_pid": 1204,
    "started_at": "2026-07-26T17:30:00-05:00",
    "version": "1.4.2",
    "command_line": "./replicator --config config.toml",
    "working_directory": "/srv/replicator"
  },
  "labels": {
    "environment": "production"
  }
}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "process_id": "server-generated-id",
    "accepted_client_run_id": "uuid-generated-by-client",
    "heartbeat_interval_seconds": 30,
    "maximum_batch_lines": 250,
    "maximum_batch_bytes": 262144
  }
}
```

The client-generated run UUID provides idempotency. Repeating `process.register` with the same tenant and client run ID must return the existing process rather than creating a duplicate.

### `stream.append`

Appends an ordered batch of console lines.

Parameters:

```json
{
  "process_id": "server-generated-id",
  "batch_id": "uuid",
  "first_sequence": 1200,
  "lines": [
    {
      "sequence": 1200,
      "timestamp": "2026-07-26T17:30:05.120-05:00",
      "stream": "stdout",
      "kind": "text",
      "text": "Downloading file 42"
    },
    {
      "sequence": 1201,
      "timestamp": "2026-07-26T17:30:05.430-05:00",
      "stream": "log",
      "kind": "json",
      "data": {
        "level": "info",
        "message": "Download progress",
        "percent": 63
      }
    }
  ]
}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "batch_id": "uuid",
    "accepted_through_sequence": 1201,
    "duplicate": false
  }
}
```

Use monotonically increasing sequence numbers per process. This allows duplicate detection, reconnection, acknowledgement, and eventual replay without prematurely creating a complex event system.

### `process.heartbeat`

Parameters:

```json
{
  "process_id": "server-generated-id",
  "timestamp": "2026-07-26T17:30:30-05:00",
  "last_sent_sequence": 1201,
  "metrics": {
    "buffered_lines": 0
  }
}
```

The `metrics` object is optional and must remain extensible.

### `process.finish`

Parameters:

```json
{
  "process_id": "server-generated-id",
  "finished_at": "2026-07-26T18:12:44-05:00",
  "status": "exited",
  "exit_code": 0,
  "last_sequence": 8451
}
```

Allowed initial statuses:

* `exited`
* `crashed`
* `stopped`
* `unknown`

### `stream.resume`

Used after reconnection to determine where transmission should resume.

Parameters:

```json
{
  "process_id": "server-generated-id",
  "client_run_id": "uuid-generated-by-client"
}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 6,
  "result": {
    "accepted_through_sequence": 1201
  }
}
```

The client should resend only lines after the acknowledged sequence.

### `process.status`

Returns the server-side status and ingestion position for the current process.

### `connection.ping`

Application-level health check when required. WebSocket protocol ping and pong frames should still be supported independently.

## Notifications

High-volume messages may eventually be sent as JSON-RPC notifications without an `id`, but the initial implementation should prefer acknowledged `stream.append` requests so delivery semantics are easy to understand and debug.

Optional future server-to-client methods:

* `server.notice`
* `server.warning`
* `client.set_log_level`
* `client.flush`
* `process.stop`
* `process.pause`
* `process.resume`

Do not implement remote process control in the initial version. Reserve the procedure names and document their future security implications.

## Delivery behavior

Implement at-least-once delivery with server-side deduplication.

Use:

* `client_run_id` to deduplicate process registration.
* `batch_id` to deduplicate whole batches.
* `sequence` to preserve ordering and detect gaps.
* Explicit acknowledgement through `accepted_through_sequence`.

Do not claim exactly-once delivery.

The client library will later combine this protocol with:

* local stdout and stderr output
* asynchronous bounded buffering
* batch transmission
* circuit breaker
* exponential backoff
* jitter
* reconnection
* replay from the last acknowledged sequence
* safe dropping policies when local limits are exceeded

## JSON-RPC errors

Define stable application error codes, for example:

```text
-32001 authentication_required
-32002 permission_denied
-32003 tenant_not_found
-32004 process_not_found
-32005 process_already_finished
-32006 invalid_sequence
-32007 sequence_gap
-32008 batch_too_large
-32009 rate_limited
-32010 incompatible_protocol_version
```

Error data should include machine-readable details where useful:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32007,
    "message": "Sequence gap detected",
    "data": {
      "accepted_through_sequence": 1198,
      "received_first_sequence": 1200
    }
  }
}
```
